# Kiro Spec Format (Multi-File Layout)

Reference for **producing or consuming** specs in the format generated by [Kiro](https://kiro.dev/docs/) (requirements-first workflow). Use this when the user works with Kiro in another window, wants to align specs with Kiro output, or wants to generate specs that can be dropped into `.kiro/specs/<spec-name>/`.

## Directory Layout

Kiro stores each spec in its own directory under `.kiro/specs/<spec-name>/`:

```
.kiro/specs/<spec-name>/
├── requirements.md   # EARS requirements, glossary, user stories, acceptance criteria
├── design.md        # Architecture, data flows, component design (often large)
├── tasks.md         # Implementation plan: tasks, subtasks, traceability, deployment order
└── .config.kiro     # Metadata: specId, workflowType (e.g. "requirements-first"), specType (e.g. "feature")
```

## requirements.md

- **Introduction**: Goal of the spec, how it fits in the system (e.g. "add observability and automated detection to the target repo").
- **Glossary**: Definitions of domain terms and acronyms (e.g. Run_ID, Data_Contract, Collector, Alarm). Critical for agents and humans to share the same vocabulary.
- **Requirements**: Numbered (Requirement 1, 2, …). Each has:
  - **User Story**: "Como [rol], quiero [objetivo], para que [beneficio]."
  - **Acceptance Criteria**: EARS-style statements: "THE &lt;entity&gt; SHALL &lt;action&gt;" or "WHEN &lt;trigger&gt; THE &lt;entity&gt; SHALL …" or "WHERE &lt;context&gt; …". Numbered (1., 2., …) for traceability.

Use **THE** + entity (e.g. THE Lambda_Function, THE Terraform_Module) and **SHALL** for mandatory behavior. Link tasks to requirements by requirement number (e.g. _Requirements: 4.1, 4.2_).

## design.md

- High-level architecture, component diagram, data flows.
- Integration points (e.g. telemetry collector, metrics backend, event bus, notification channel).
- Constraints: tech stack, existing patterns, non-functional (e.g. no new cloud account).
- Can be large; split by section (e.g. Data Contract, Alarms, Functions, Event routing, etc.).

## tasks.md

- **Overview**: Short summary of the implementation approach (e.g. "phased approach: module structure, core components, testing, integration").
- **Tasks**: Hierarchical list with checkboxes:
  - Top-level: `- [ ] 1. Create module structure`
  - Subtasks: `- [ ] 2.1 Create storage resource` with indentation.
- **Traceability**: Each task or subtask ends with `_Requirements: 4.6, 9.1_` (requirement IDs from requirements.md).
- **Notes**: Deployment order, directory structure, implementation language (e.g. Python 3.11), optional vs required tasks (e.g. tasks marked `*` for optional tests).
- **Directory structure**: Optional ASCII tree of where artifacts live (e.g. `infra/module-name/`, `config/`, `docs/adr/`).

When **producing** a spec for Kiro (or Kiro-compatible tooling), output these three files and optionally `.config.kiro` with `workflowType: "requirements-first"` and `specType: "feature"`.

## .config.kiro

JSON metadata, e.g.:

```json
{"specId": "<uuid>", "workflowType": "requirements-first", "specType": "feature"}
```

## Relationship to feature-spec-and-tasks (Single-Doc)

The skill `feature-spec-and-tasks` produces a **single** spec document (Overview, Requirements, Design, Tasks, Documentation, Before executing). The **content** is the same in spirit:

| Single doc (skill) | Kiro multi-file        |
|--------------------|------------------------|
| Overview           | requirements.md intro  |
| Requirements (EARS)| requirements.md        |
| Design             | design.md              |
| Tasks (Tickets)    | tasks.md               |
| Documentation      | tasks.md or design.md  |
| Before executing   | tasks.md Notes or intro|

When the user says they use **Kiro** or have a spec in `.kiro/specs/`, prefer or align with the **multi-file** layout so the output can be pasted into Kiro's directory. When generating from scratch and the user does not mention Kiro, the single-doc format remains the default.

## Example: Kiro spec layout (generic)

A typical Kiro spec in `.kiro/specs/<your-spec-name>/` contains:

- **requirements.md**: Introduction, **Glossary** (Run_ID, Data_Contract, Collector, Alarm, etc.), then numbered Requirements (1, 2, …) each with User story and **numbered acceptance criteria** (1., 2., …). Entities use **THE &lt;Glossary_term&gt;** for consistency.
- **design.md**: Architecture, data flows, integration points (collector, metrics backend, event bus, notifications), constraints, and component design. Often large; split by section.
- **tasks.md**: Overview, hierarchical tasks with checkboxes (1., 2.1, 2.2, …), each with `_Requirements: X.Y_` for traceability. Notes include deployment order, directory structure (ASCII tree), implementation language, and which tasks are optional (e.g. marked `*`).

Use this layout when the user works with Kiro or when the initiative is large (e.g. 15+ requirements, 20+ tasks). The single-doc format in `ears_and_format.md` maps to these three files as in the table above.
